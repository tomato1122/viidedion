# 設計書の波及監査

このプロジェクトは**設計書が一次情報**で、実装はその写し。逆ではない。
設計書が古いまま残ると、**それを読んだ側が古い設計を実装する**。

実際に起きたこと: ADR-001 で「再計算目的の永続キャッシュは Azure Maps の規約違反」と
判定した後も、`docs/02` のコスト表は「`spot_poi_cache` で必ずキャッシュ」と
指示し続けていた。実装だけ直して設計書を放置した結果。

## 使いどき

- `db/migrations/` にファイルを足した
- `core/` `worker/` `jobs/` `ingest/` `api/` を触った
- 外部サービスの採否を変えた（ADRを書いた／却下した）
- タスクの状態が変わった
- **コミットまたはPR作成の直前**

## 手順

### 1. 変更範囲を出す

```bash
git status --short
git diff --stat HEAD
```

### 2. 波及表を引く

`CLAUDE.md` の「変更の波及表」を読み、変更したものに対応する行の**確認先をすべて開く**。
記憶で判断しない。

### 3. 機械的に拾えるものを拾う

```bash
# 却下したはずの外部サービスが設計書に残っていないか
grep -rn 'Azure Maps' docs/ | grep -v 'docs/06'

# 規約違反と判定したキャッシュ設計が残っていないか
grep -rn 'spot_poi_cache' docs/

# 実装済みなのに「未着手」、未実装なのに実装済みに読める記述
grep -rn '未着手\|未実装\|想定\|予定' docs/02-azure-architecture.md

# テスト件数・アサーション数の記述が実測とずれていないか
grep -rn 'アサーション\|ケース' docs/ CLAUDE.md
```

ヒットしても直ちに誤りとは限らない。**「旧 → 新」の対照表や ADR の却下理由は残すのが正しい**。
現行の指示として読めるかどうかで判断する。

### 4. 擬似コード・図・表の「本体」を見る

**注記を足して本体を放置していないか。** これが一番見落とす。

- `docs/01` の擬似コードブロック
- `docs/02` の mermaid 構成図
- `docs/02 §7` のコスト表
- `docs/01 §5` のテーブル表

欄外に「§10 で置き換わった」と書いても、読む側は擬似コード本体を写経する。
**本体を直す。**

### 5. 実装状態の対応表を更新する

`docs/02 §9`「実装との対応」に、構成要素とコードと状態（✅ / 未着手）の対応がある。
デプロイ単位やモジュールを足したら必ずここを更新する。
**未実装を「ある」ように書かない。**

### 6. タスク状態は両方そろえる

`docs/03-remaining-tasks.md` と Notion の
[残タスク一覧](https://app.notion.com/p/3ba7066098c28199b6cfd5a5254dce31) は同じ内容。
**片方だけ更新しない。** Notion 側は忘れやすいので最後に必ず確認する。

### 7. 設計と実装がずれた場合の扱い

実装中に「設計書のとおりに作ると壊れる」と分かることがある（実際に `docs/01 §8.3` の
系譜判定で起きた）。そのときは:

1. **設計書を直す。** 実装だけ変えて設計書を残すと、次の人が同じ罠を踏む
2. **なぜ変えたかを書く。** 「距離だと res9/res10 のセル中心が100mずれる」のような、
   再発見にコストがかかる理由を残す
3. 判断が大きければ ADR にする（`docs/06` の形式）
4. コミットメッセージとPR本文にも書く

## 出力

確認した項目と、更新した設計書の一覧を短く報告する。
更新不要と判断した場合は**なぜ不要か**を1行で述べる（「確認した」だけにしない）。
