### T-05 POIソースのライセンス条件ADR 【完了】

**出典**: B-11
**✅ 完了（2026-08-12）**: [docs/06-adr-poi-source.md](06-adr-poi-source.md)（ADR-001）。

**調査で分かったこと**: **現行の `spot_poi_cache` の設計は Azure Maps の規約に反していた。**
規約はキャッシュを latency 低減目的に限り、保持を最大6か月に制限している。
「再計算時のAPI課金とレート制限の回避」を目的とする永続キャッシュは
「scaling such Results to serve multiple users」に該当する。

**決定**: MVPのPOIソースは **OpenStreetMap（ODbL）**。地域抽出を自前の PostGIS に
取り込み、外部POI APIは呼ばない。`docs/01 §4.3` の再計算設計が生き残る唯一の選択肢だった。

**実装済み**:
- `spot_source` の各列を確定（採用は `adopted` で1つに制約）
- `poi_reference` / `poi_extract_versions`（抽出のバージョニング。再現性のため）
- `find_scenic_poi()` が `docs/01 §1.2 手順5` の外部API呼び出しを置き換え
- `spot_poi_cache` に保持上限を **CHECK 制約**として書き込み（180日超は INSERT 不可）
- `v_poi_license_compliance`（帰属表示欠落と期限超過の監視）

**残作業**: OSM の日本の `tourism=viewpoint` カバレッジ測定（T-10 と同時）。
薄ければ「POIを使わない」案に退避する（docs/06 §5）。カテゴリ正規化規則の確定は T-15。

## T-21 の持ち越しは回収済み

T-16（DBSCAN昇格）が投稿の紐付けを張り替えると、`post_rarity_scores` と
`spot_facet_stats` が実態とずれる、という宿題があった。**T-21 で回収した。**

| 宿題 | 回収方法 |
|---|---|
| 昇格後の②希少性が古い | `jobs/recalc_grain.py --rarity-only`。スポットを動かさないので配信中でも実行できる。**昇格バッチの後に回すこと** |
| ファセット統計が旧スポットのまま | 同上。`recompute_rarity_for_grain()` が作り直す |
| `split` の判定 | 再計算の `lineage` フェーズ（`finalize_spot_lineage()`）。全件揃ってから親ごとの子の数を数える |

### 実装で見つかった不具合（T-15 に遡って修正）

同一粒度では identity ごとに実体は1つしか持てないのに、`core/spots.py` が親 identity を
無条件に引き継いでいた。同じ親を2つの実体が引き継ごうとすると
`upsert_spot_with_identity` の `ON CONFLICT` に当たり、**離れた2地点が黙って1つの
スポットに潰れ、重心が後から来た方に動いていた**。

粒度を細かくする再計算（1スポットが2つに割れる場面）でしか出ないので、通常の取り込みでは
気づけない。`_claim_identity()` で親が既に引き継がれていたら新しい identity を発行し、
`split` として記録するように直した（docs/01 §8.3）。

## T-30 初期ユーザーゼロ期の体験設計 【新規】

**問題**: 3層スコアはいずれも「他の投稿が既にあること」を前提にしている。
ローンチ直後はその前提が成立せず、設計上の主要機能が全部空回りする。

| 層 | ゼロ期に起きること |
|---|---|
| ② 希少性 | 全スポットの累計投稿が0 → `base` が常に最大18点。全ファセットが「初」→ +8点。**全投稿が26点で並び、希少性という情報が何も伝わらない** |
| ③ コミュニティ | 投票者がいない → `vote_count = 0` → 全投稿が中央値10点で並ぶ |
| ランキング | T-02 の階段を全段落ちて発見表現に倒れる。動作としては正しいが、**全員が「発見」だと発見の価値も消える** |

③ について、票ゼロを減点ではなく中央値に寄せる現在の設計（`calc_community_score` の
ベイズ縮約）は、それ自体がコールドスタート耐性として既に機能している。
**本当の問題は点の付け方ではなく、比較投票のペアが供給されないこと。**

### 設計案

いずれも `scoring_rulesets.weights` と `ranking_facet_levels` で表現でき、
スキーマ変更は不要。**実装は T-24（配点確定）とまとめて行うのが妥当。**

**(a) 希少性の基準値を投稿密度に連動させる**
`rarity_n_ref` を固定500ではなく「全スポットの `post_count` の p90」に連動させるモードを足す
（`rarity_n_ref_mode: fixed | adaptive_p90`）。初期は p90 が小さいので、
累計1件と3件の差でも `base` に差が出る。密度が上がれば固定値と一致していく。

**(b) 「初」ボーナスにスポット成熟度の条件を足す**
累計投稿が1件目のスポットでは `first_combination` を出さない。
1件目は定義上必ず「初」なので、ボーナスとしての情報量がゼロ。
代わりに発見表現（`new_scenery`）で受ける——T-02 の受け皿がそのまま使える。

**(c) 投票を投稿の対価にする**
比較投票のペア供給をユーザー行動で作る。投稿フローに「2ペア投票してから投稿」を挟む。
投稿数 N に対して投票数が線形に増えるので、③ が機能し始めるまでの時間が縮む。
T-09（比較グラフの接続性）と同じ問題を入口側から解く手段でもある。

**(d) ローンチ範囲を地理的に絞る**
全国同時ではなく1エリア（例: 関東の山岳・海岸）から始める。同一スポットへの投稿密度が
上がり、②③ とランキング階段が早く機能する。**プロダクト判断であり、技術的な作業ではない。**

**完了条件**: (a)〜(d) の採否が決まり、採用したものが `scoring_rulesets` か
ローンチ計画のどちらかに落ちている。
