## Phase 0 — 実装前に埋める設計の穴

レビューの「最優先」指摘のうち、**まだ設計に反映できていないもの**。
ここを埋める前に本番前提の実装へ進まないこと。

### T-03 不正対策を trust_score の段階判定へ 【最優先】

**出典**: B-05
**問題**: 引継ぎ書の「EXIFと画像ハッシュで転載と位置偽装はほぼ潰せる」は成立しない。
位置・日時メタデータは削除・変更でき、ハッシュは再圧縮・トリミング・スクリーンショットで変わる。
現在のスキーマは各チェックの pass/fail を持つだけで、**総合的な信頼度がない**。

**対応**:
- `posts.trust_score` を導入し、断定ではなく段階判定にする
- シグナルを増やす: 画像埋め込みによる近似検索、アプリ内カメラ撮影の証跡、
  投稿速度・移動可能性（前回投稿地点からの物理的到達可能性）、アカウント履歴
- pHash だけでなく完全一致ハッシュも併用

**完了条件**: 各シグナルの重みと、trust_score 帯ごとの扱い（公開・スコア抑制・レビュー送り）が定義される。

---

### T-04 位置情報プライバシー・公開安全要件 【最優先】

**出典**: B-06
**問題**: 正確な撮影地点の公開は、自宅・子どもの行動範囲・希少動植物の生息地・
危険区域を露出させる。現在は EXIF除去と `location_privacy` カラムまでしか対応していない。

**対応**:
- 自宅付近・保護地域・危険地点の座標をぼかす仕組み（ユーザー登録の自宅周辺 + 保護区データ）
- 人物・顔・車両ナンバーの検出と公開前確認
- 私有地・立入禁止区域への投稿および誘導の対策
- 位置情報の保存期間・利用目的・削除手順の定義

**完了条件**: プライバシー方針が文書化され、ぼかし処理がパイプラインに組み込まれる。

---

### T-05 POIソースのライセンス条件ADR 【最優先】

**出典**: B-11
**問題**: `spot_poi_cache` を設計したが、**採用予定の Azure Maps のキャッシュ・保存条件を
確認していない**。プロバイダによっては応答の永続キャッシュや再配布が制約される。
Google Places は保存・キャッシュ・帰属表示に制約があり、OSM は ODbL の帰属と
派生データベースの扱いが要る。

**対応**: MVPで使うPOIソースを1つに絞り、保存可能な項目・保持期間・更新方法・
帰属表示・料金をADRに残す。**キャッシュが不可なら再計算ジョブの設計（docs/01 §4.3）を見直す。**

**現状**: T-01 で `spot_source` テーブルを作り、ADRの結論を入れる場所は用意した。
`cache_allowed` / `cache_max_age_days` / `redistribution_allowed` / `attribution_text` が
すべて NULL のままなのは「未確認」を意味する。スモークテストがこれを検査している。

**完了条件**: ADRがあり、`spot_source` の各列が埋まり、`spot_poi_cache` の保持ポリシーが利用規約と整合している。

### T-31 認証・アカウント基盤 【最優先・新規】

**問題**: T-01〜T-29 に認証の項目が無かった。`docs/02 §1.1` が「認証済み」を前提に
ユーザー委任SASを発行する設計になっているが、**その認証自体が未設計**。
`users` テーブルには外部IDプロバイダの被写体識別子を入れる列すら無い。

**対応**:
- Entra External ID（旧 Azure AD B2C）でのサインイン方式とトークン検証
- `users` に外部IDの対応列を足す（プロバイダ + subject の複合一意）
- API 側のトークン検証と、SAS発行の認可境界
- 退会時のデータ削除範囲（投稿・投票・ランキング履歴をどこまで消すか）

**注記**: 別セッションが同時に着手している領域。**着手前に成果の有無を確認すること。**

**出典**: B-10

**出典**: B-04

### T-10 H3解像度 9 / 10 の決定

**依存関係の注意**: この調査には投稿を集めるクライアントが必要だが、クライアント実装方式

**どちらかを仮決めして先に進めないと止まる。** 推奨は「使い捨て前提の簡易クライアントで

### T-12 天候APIの選定

## T-30 初期ユーザーゼロ期の体験設計 【新規】

**問題**: 3層スコアはいずれも「他の投稿が既にあること」を前提にしている。
ローンチ直後はその前提が成立せず、設計上の主要機能が全部空回りする。

| 層 | ゼロ期に起きること |
|---|---|
| ② 希少性 | 全スポットの累計投稿が0 → `base` が常に最大18点。全ファセットが「初」→ +8点。**全投稿が26点で並び、希少性という情報が何も伝わらない** |
| ③ コミュニティ | 投票者がいない → `vote_count = 0` → 全投稿が中央値10点で並ぶ |
| ランキング | T-02 の階段を全段落ちて発見表現に倒れる。動作としては正しいが、**全員が「発見」だと発見の価値も消える** |

③ について、票ゼロを減点ではなく中央値に寄せる現在の設計（`calc_community_score` の
ベイズ縮約）は、それ自体がコールドスタート耐性として既に機能している。
**本当の問題は点の付け方ではなく、比較投票のペアが供給されないこと。**

### 設計案

いずれも `scoring_rulesets.weights` と `ranking_facet_levels` で表現でき、
スキーマ変更は不要。**実装は T-24（配点確定）とまとめて行うのが妥当。**

**(a) 希少性の基準値を投稿密度に連動させる**
`rarity_n_ref` を固定500ではなく「全スポットの `post_count` の p90」に連動させるモードを足す
（`rarity_n_ref_mode: fixed | adaptive_p90`）。初期は p90 が小さいので、
累計1件と3件の差でも `base` に差が出る。密度が上がれば固定値と一致していく。

**(b) 「初」ボーナスにスポット成熟度の条件を足す**
累計投稿が1件目のスポットでは `first_combination` を出さない。
1件目は定義上必ず「初」なので、ボーナスとしての情報量がゼロ。
代わりに発見表現（`new_scenery`）で受ける——T-02 の受け皿がそのまま使える。

**(c) 投票を投稿の対価にする**
比較投票のペア供給をユーザー行動で作る。投稿フローに「2ペア投票してから投稿」を挟む。
投稿数 N に対して投票数が線形に増えるので、③ が機能し始めるまでの時間が縮む。
T-09（比較グラフの接続性）と同じ問題を入口側から解く手段でもある。

**(d) ローンチ範囲を地理的に絞る**
全国同時ではなく1エリア（例: 関東の山岳・海岸）から始める。同一スポットへの投稿密度が
上がり、②③ とランキング階段が早く機能する。**プロダクト判断であり、技術的な作業ではない。**

**完了条件**: (a)〜(d) の採否が決まり、採用したものが `scoring_rulesets` か
ローンチ計画のどちらかに落ちている。

## 進め方の推奨

1. **Phase 0 の残り4件（T-03 / T-04 / T-05 / T-31）を潰す。** レビューの判定は「条件付き保留」で、
   最優先項目を設計に反映してから本番前提の実装へ進むこととされている。
   スキーマ変更を伴う T-01 / T-02 は完了したので、**残りは設計と外部規約の確認が中心**。
   このうち T-05 は結論次第で docs/01 §4.3（再計算ジョブ）を書き換えるため、先に潰す価値が高い。
2. **T-10 / T-11 は実データが要る**ので、プロトタイプで先に投稿を集め始める。
   T-11 と T-20 は相互依存しているので、使い捨てクライアントで T-11 だけ先に取る。
3. Phase 2 の実装は Phase 0・1 の決定に依存する。順序を飛ばすと作り直しになる。
4. **T-30 は T-24 とまとめる。** 単独で実装するとスキーマではなく重みの問題なので二度手間になる。
