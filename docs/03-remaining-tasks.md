## Phase 0 — 実装前に埋める設計の穴

レビューの「最優先」指摘のうち、**まだ設計に反映できていないもの**。
ここを埋める前に本番前提の実装へ進まないこと。

> 2026-08-12: T-03 / T-04 は設計完了（docs/04）。残る設計の穴は **T-01 / T-02 / T-05** の3件。

### T-01 スポットの永続IDと系譜 【最優先】

**出典**: B-01
**問題**: 現在のスキーマは `spots` を粒度バージョンごとに作り直す。つまり **粒度を変えると
スポットのIDが変わる**。「先週◯◯展望台で1位」の称号、スポット詳細ページのURL、
ユーザーの「訪問したスポット」履歴が、粒度変更のたびに切れる。

**対応**:
- `spot_identity`（粒度に依存しない永続ID）を新設し、`spots` はその versioned な実体にする
- `spot_alias`（別名・旧ID）
- `spot_lineage`（分割・統合履歴。粒度を細かくすると1スポットが2つに割れる）
- `spot_source`（POI提供元・ユーザー作成の区別。現在は `poi_source` のみ）

**完了条件**: 粒度を変更しても、スポットのURLと称号履歴が維持される。分割・統合を表現できる。

---

### T-02 ランキング成立条件のフォールバック階段 【最優先】

**出典**: B-03
**問題**: 現在は「投稿5件未満のファセットはランキングを作らない」だけ。**作らなかった場合に
何を見せるかが未定義**。ファセットを掛け合わせるほど過疎化するのに、受け皿がない。

**対応**: 母数を満たさない場合に軸を段階的に落とす。
1. スポット × 方位 × 天候 × 時間帯
2. スポット × 方位 × 時間帯
3. スポット × 時間帯
4. スポット全体

どれも成立しない場合は順位を出さず、**「この条件で最初の記録」「新しい景色を発見」**という
発見・記録系の表現に切り替える（これは表示ポリシーとも整合する）。
最低ユニーク投稿者数の条件も追加する（1人の連投でランキングが成立しないように）。

**完了条件**: 全ファセットについて、順位を出すか発見表現にするかが一意に決まる。

### T-05 POIソースのライセンス条件ADR 【最優先】

**出典**: B-11
**問題**: `spot_poi_cache` を設計したが、**採用予定の Azure Maps のキャッシュ・保存条件を
確認していない**。プロバイダによっては応答の永続キャッシュや再配布が制約される。
Google Places は保存・キャッシュ・帰属表示に制約があり、OSM は ODbL の帰属と
派生データベースの扱いが要る。

**対応**: MVPで使うPOIソースを1つに絞り、保存可能な項目・保持期間・更新方法・
帰属表示・料金をADRに残す。**キャッシュが不可なら再計算ジョブの設計（docs/01 §4.3）を見直す。**

**完了条件**: ADRがあり、`spot_poi_cache` の保持ポリシーが利用規約と整合している。

## Phase 1 — 判断を確定させる検証

### T-06 Azure構成ADR（非機能要件ベース）

**出典**: B-12
モデルサイズ・応答時間・GPU要否・月間投稿数を先に決めてから構成を確定する。
現在の選定は理由付きだが、数値の裏付けがない。概算費用も含める。

### T-07 日本景観データでの特徴量検証計画

**出典**: B-07, B-08
フラクタル次元の「D=1.4 頂点の固定山型配点」と「空は正・雲は負」は、いずれも
限定条件の研究からの飛躍。**初期特徴量候補**と位置づけ、日本の景観データで
効果量を確認してから配点を決める。景観カテゴリ・時間帯・雲種との交互作用も見る。

### T-08 Scenic-Or-Not の性能値整理

**出典**: B-10
「elastic net で Kendall 0.544」と「VGGベースCNNで 0.658」は別モデルの値。
モデル名・入力特徴・学習方法・評価セット・相関を表で分離し、実装目標を明確にする。

### T-09 比較投票アルゴリズムの選定

**出典**: B-04
現在は Elo + ベイズ縮約。レビューは TrueSkill / Bayesian Bradley–Terry を比較候補に挙げている。
推定値に加えて**不確実性・比較回数・比較グラフの接続性**を保存する必要がある。
投票UIに「同程度」「判断不能」「スキップ」も用意する。

### T-10 H3解像度 9 / 10 の決定

実データ200〜500件を集め、`v_grain_health` の指標で判断する（docs/01 §6）。

### T-11 方位取得可能端末の比率調査

実機検証。`GPSImgDirection` が取れる端末が5割を切るなら8分割を4分割に落とす。
クライアント実装方式（ネイティブ / Flutter / React Native）の判断もこれに依存する。

### T-12 天候APIの選定

Azure Maps Weather の履歴実況 vs 気象庁アメダス。日本での粒度と課金で比較。

## 進め方の推奨

1. **Phase 0 の5件を先に潰す。** レビューの判定は「条件付き保留」で、最優先5項目を
   設計に反映してから本番前提のスキーマ・ランキング・スコア確定処理へ進むこととされている。
   このうち T-01 と T-02 はスキーマ変更を伴うので、実装が進むほど手戻りが大きい。
2. **T-10 / T-11 は実データが要る**ので、プロトタイプで先に投稿を集め始める。
3. Phase 2 の実装は Phase 0・1 の決定に依存する。順序を飛ばすと作り直しになる。
