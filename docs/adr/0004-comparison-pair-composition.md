# ADR-0004: 比較ペアの構成を階層的にし、橋渡しで接続性を保つ

- **状態**: 承認（2026-08-13）。**実装は T-09（アルゴリズム選定）の後**
- **決定者**: 開発者
- **関連**: P-04b / レビュー指摘 B-04 / T-09 / `db/migrations/0004_scoring.sql` / `docs/04-security-design.md §7`

## 背景

比較投票では**サーバーが2枚を選んで提示する**（`docs/04 SEC-VOTE-01`。クライアントに
指定させると狙った投稿を持ち上げる攻撃が成立するため）。残っていたのは**どういう基準で
2枚を選ぶか**である。

Elo のような比較ベースの評価には「**比較グラフの接続性**」という性質がある。
A–B と B–C を比べれば A–C の差も推定できるが、2つのグループが一度も比較されなければ、
両者のレーティングは**別々の物差し**になり比較できない。これは設計レビュー B-04 の指摘である。

P-01 で「全国 × ライト層」を選んだ結果、ファセット（スポット × 方位 × 天候 × 時間帯 × 季節）
あたりの投稿が1〜2件になり、**ファセット内でペアを組もうとすると相手がいない**状態になった。

トレードオフの本質は次の通り。

- **局所に寄せる**ほど比較の意味は明確になるが、票が集まらず③が動かない
- **横断に寄せる**ほど票は集まるが、「雪の峠 vs 夏の海岸」の比較になり、
  実質「写真としての良さ」を測ることになる。これは**①AI採点と役割が重複**し、
  ③をハイブリッド採点に入れた理由（AIの偏りを人間の評価で補正する）が失われる

## 決定

ペアを次の優先順位で引く。上位の段で組めなければ下の段に落ちる。

| 段 | 引く範囲 | 位置づけ |
|---|---|---|
| 1 | 同一ファセット（スポット × 方位 × 天候 × 時間帯 × 季節） | **主戦場** |
| 2 | 同一スポット（条件は問わない） | **主戦場** |
| 3 | **同じ時間帯 × 天候の別スポット** | フォールバック |
| 4 | 横断（橋渡し。意図的に一定割合を混ぜる） | 最終段 |

**第3段の定義が要点。** 「何でもいいから別スポット」ではなく「同じ時間帯×天候の別スポット」に
限定する。「雪の峠 vs 夏の海岸」ではなく「**別々の場所の、同じ朝焼け**」を比べる形にすることで、
場所が違っても比較の意味が保たれ、①との重複を避けられる。

第4段の橋渡しは、局所比較だけでは比較グラフが分断されるため、**接続性を保つ目的で
意図的に混ぜる技術的措置**である。評価軸を人気に戻すものではない。

あわせて次を必須とする。

- **自己投票の除外**: ペア選定から `posts.author_id = voter_id` を除外する。
  P-04（投稿フローに投票を組み込む）と第1〜2段（同一スポット優先）を組み合わせると、
  投稿直後のユーザーに自分の写真が提示され得るため
- **相互投票ループの検知**: 少数のユーザーが小さなスポットで互いに投票し続ける
  閉じたループを日次バッチで検出する

## 影響

### スキーマ

| 対象 | 変更 |
|---|---|
| `votes` | `pair_tier`（facet / spot / similar / bridge）とファセット列を追加 |

現在の `votes`（`0004_scoring.sql`）は `grain_version_id` と `spot_id` しか持たないが、
コメントには「監査用。どのファセットの比較として提示したか」と書かれており、
**実装が伴っていなかった**。本決定でこの不整合を解消する。**未実装**（T-09 選定後に着手）。

**`post_community_scores.elo_rating` は1列のままでよい。** 投稿は（粒度バージョンごとに）
ちょうど1つのファセットに属するため、局所比較でも横断でも1列で足りる。

### Elo の解釈が変わる

`calc_community_score` は固定基準 `elo_ref = 1500` に対する期待勝率で 0〜20点に写す。
本決定により Elo は「**所属プール内での相対位置**」の性格を帯びるため、
プールの強さの違いが点数に混入する。

ただし縮約（`community_shrink_m = 8`）が効くため、票が少ないうちは10点付近に留まり破綻しない。
**関数の変更は不要**だが、Elo の意味が「全体の中での強さ」から
「局所プール内の位置 ＋ 橋渡しによる粗い較正」に変わったことを記録する。

### T-02 との関係（混同注意）

T-02（ランキング成立条件のフォールバック階段。実装: `0009_ranking_fallback.sql`）と
思想は同じだが、**段数が違う**。

| | 最終段 |
|---|---|
| T-02（ランキング） | 「スポット全体」。それも不成立なら**順位を出さない**（`post_discovery_labels`） |
| 本決定（ペア） | 「橋渡し」。**常に成立する** |

本決定の方が1段深い。実装で「同じ関数で両方やる」と齟齬が出るため、共通化しすぎないこと。

### 認識済みのトレードオフ

第1〜2段を主戦場に据えたため、**投稿が少ないスポットでは③に票がほとんど入らない**。
縮約により③は10点前後に張り付き、多くの投稿で実質「①+②」が点数を決める。
これは破綻ではなく「①②が主・③が補正」という構成になるだけであり、意図した姿である。

## 却下した案

- **ファセット内限定**: 比較の意味は最も明確だが、P-01 の下ではペアがほぼ組めず③が機能しない
- **横断（グローバル）のみ**: 常にペアが組めるが、③が①の焼き直しになる

## 未解決

- 各段の**実際の充足率**は実データ待ち。第1〜2段が想定より空振りするなら、
  第3段の条件（時間帯×天候）の緩め方を再検討する
- 橋渡しの混入比率（初期案は1割）の妥当性は未検証
- **T-09（Elo / Bayesian Bradley–Terry / TrueSkill の選定）は本決定を前提に行う。**
  局所比較が主体になるため、推定値だけでなく**不確実性**を保持できる手法が有利になる可能性がある
