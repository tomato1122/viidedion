# プロダクトとして決めなければいけないこと

> docs/01〜04 で技術設計（粒度・インフラ・スキーマ・セキュリティ）はかなり進んだ。
> 一方で **プロダクトの根幹に未定義の空白がある**。この文書はそれを列挙する。
>
> ここに挙げたものは技術で解けない。**決めるしかない**種類の問いであり、
> かつ多くが「決めないと技術側の数値も決まらない」依存を持っている。
>
> 既に docs/03 の Phase 3 に挙がっている項目（T-24〜T-29）は §C に再掲するだけに留める。

---

## A. 決めないと他が決まらない（ブロッカー）

### P-01 ターゲットユーザーと地理スコープ

**決めること**: 誰のためのアプリか。そして **最初にどの範囲で始めるか**。

**決めないと止まるもの**: ほぼ全部。特に —— H3解像度（T-10）、ランキング足切り5件の妥当性、
スポット粒度の失敗モード閾値（docs/01 §6）は、**すべて「1スポットあたり何件投稿が集まるか」に
依存する**。密度が決まらないと数値が決まらない。

**選択肢**:

| | ターゲット | 密度 | 帰結 |
|---|---|---|---|
| a | カメラ趣味層・全国 | 低い（薄く広く） | スポットが1件ずつ散らばり、ランキングがほぼ成立しない |
| b | ライト層・全国 | 中 | 有名スポットだけ密集し、無名スポットは砂漠 |
| c | **特定地域から開始**（例: 首都圏近郊の山・海岸・展望台） | 高い | 椅子が成立する。ただし初期の市場が小さい |

**推奨**: **c**。この設計は「1スポットに複数人の投稿が集まる」ことを前提に組んである
（ランキング5件足切り、比較投票、DBSCAN昇格の `dbscan_min_users=3`）。
全国に薄く広げると、**自分で作った足切りルールによって椅子がゼロになる**。
地域を絞れば密度が作れ、T-10 / T-11 の実データ収集も同時に進む。

### P-02 アプリを開いたとき、最初に何が見えるか

**決めること**: ホーム画面。フィードの構成原理。

**現状**: **docs にフィードの記述が一行も無い。** 投稿・採点・ランキングは設計したが、
「ユーザーが何を眺めるアプリなのか」が定義されていない。

**決めないと止まるもの**: API設計（T-19）、クライアント実装（T-20）、そして
**投票の供給**（P-04。投票導線をどこに置くかはフィード設計そのもの）。

**選択肢**:

| | ホームの中心 | 性格 |
|---|---|---|
| a | 時系列の投稿一覧 | Instagram型。フォローが無いと只の新着順になる |
| b | **地図** | 「どこに絶景があるか」の探索。このアプリの資産（スポット）と一致 |
| c | **ランキング／部門一覧** | 「今週の朝焼け部門」を見に来る。週次リセットと噛み合う |
| d | 比較投票そのもの | Tinder的。投票供給は最大化されるが、閲覧体験が痩せる |

**推奨**: **b + c のハイブリッド**（地図で探し、スポットを開くと部門別ランキングが出る）を
基本に、**d を「1日◯回」の軽いループとして併設**。
a を中心に据えるのは避ける —— 時系列フィードは結局フォロワー数が効く構造を呼び戻し、
プロダクトの中核思想（docs/00 §1）と衝突する。

### P-03 ソーシャルグラフを持つか

**決めること**: フォロー機能の有無。持つなら、それが何に効いて何に効かないか。

**論点**: 中核思想は「フォロワー数が権力にならない」であって、「人と人が繋がらない」ではない。
だが安易にフォローを入れると、**フィードの並び順という形でフォロワー数が復権する**。

**選択肢**:
- a. フォロー無し（スポットのみをフォロー対象にする）
- b. **フォローはあるが、スコア・ランキングには一切影響しない**。影響するのは「その人の新着を見逃さない」だけ
- c. 通常のSNS同様

**推奨**: **b**、ただし **フォロワー数を非表示にする**（自分だけが自分のフォロワー数を見られる、
あるいは完全非表示）。表示ポリシー（docs/00 §3）で点数を隠したのと同じ理屈が、
フォロワー数にもそのまま当てはまる。数を見せた瞬間にそれが競争軸になる。

### P-04 投票の供給をどう作るか

**決めること**: 誰が、なぜ、どれだけ投票するのか。

**これは設計上の穴として最も危険。** ③コミュニティ加点（0〜20点）は投票が集まる前提で
組んであるが、**投票を促す仕組みが何も設計されていない**。

投票が集まらないとどうなるか —— `calc_community_score` はベイズ縮約で中央値に寄るので、
**全投稿が一律10点になる**。つまり ③ が消滅し、実質「①AI + ②希少性」だけのアプリになる。
壊れはしないが、ハイブリッド採点を採った理由（AIの偏りを人間の評価で補正し、
日本向けにファインチューニングする原資を作る）が丸ごと失われる。

**必要な供給量の目安**（`community_shrink_m = 8` から逆算）:

| | 値 |
|---|---|
| 1投稿あたり必要な票数 | 15〜30票（confidence 0.65〜0.8 相当） |
| 1回の比較投票が生む票 | 2票（2枚を並べるため） |
| DAU の20%が毎日投稿すると仮定 | **アクティブユーザー1人あたり 2〜4回/日の投票が必要** |

数字自体は非現実的ではない。だが **「1人あたり毎日2〜4回投票する」は設計して初めて起きる行動**であり、
放っておいて起きるものではない。

**選択肢**（併用可）:
- 投稿の対価にする（投稿するには数回投票する。供給と需要が自動的に釣り合う）
- 自分の結果閲覧の導線に挟む（「昨日の結果を見る前に3枚選ぶ」）
- 訪問済みスポットの投票を優先提示（docs/00 §2③ の重み付け案と一致し、動機も自然）
- 投票自体に報酬（称号・T-25 と接続）

**あわせて決めること**: **ペアをファセット内から引くか、横断で引くか。**
ファセット内に限ると比較として意味が明確になるが、**票がファセット数だけ分散して
1つも収束しない**（レビュー B-04 の「比較グラフの接続性」）。横断で引くと票は集まるが、
「雪の峠 vs 夏の海岸」を比べることになる。**T-09 と一体で決める必要がある。**

### P-05 投稿頻度の前提と「過去に撮った写真」の扱い

**決めること**: このアプリは週に何回開かれ、月に何回投稿されるサービスなのか。
そして **旅行から帰った後・何年も前に撮った写真を投稿できるのか。**

**論点**: 絶景は日常的に撮れない。Instagram は毎日撮れるが、風景は月1回かもしれない。
週次リセット（毎週椅子が空く）は良い設計だが、**投稿が月1回のユーザーにとって
週次リセットは「ほぼ毎回、参加していない週」になる**。

**既存設計との矛盾（要修正）**: docs/04 の `exif_time_match` は
**EXIF撮影時刻と投稿時刻の乖離が7日を超えると trust_score を -0.15 する**。
これは「旅行から2週間後にまとめて投稿する」という**きわめて自然な行動を減点する**。
セキュリティ側のパラメータとして置いたが、実質はプロダクトの意思決定である。

**選択肢**:
- a. 撮って即投稿のみを想定（7日ルール維持。リアルタイム性重視だが、絶景の性質と合わない）
- b. **過去写真を許容し、「撮影日ベース」でランキング期間に参加させる**
  （7日ルールを撤廃し、代わりに「撮影日が今週」のものだけ今週の椅子に入れる）
- c. 過去写真は投稿できるがランキング対象外（アーカイブ扱い）

**推奨**: **b**。ランキングの所属を `posted_at` ではなく `captured_at` で決める。
ただしこれは `rebuild_ranking_entries` が現在 `posted_at` で期間を切っているため、
**実装変更を伴う**（`db/migrations/0005_ranking.sql`）。決めたら早めに直すこと。

## B. 体験の骨格

### P-06 コールドスタートで何を見せるか

**決めること**: ユーザーが10人・投稿が30件しかない時期に、アプリは何を表示するのか。

**問題**: 自分で置いたルールがそのまま初期体験を殺す。
- ランキングは投稿5件以上のファセットのみ（`ranking_min_facet_posts = 5`）→ **初期は椅子ゼロ**
- ③は24時間で確定するが投票者がいない → **全員10点**
- 希少性②は初期こそ最大（誰も投稿していないので base 18点満点）→ **ここだけは初期に強い**

**推奨の方向**: 初期は **「競争」ではなく「発見と記録」** を前面に出す。
②希少性が初期に最も高く出る性質は追い風なので、
「このスポットの最初の記録」「日本で◯人目」という表現を主役にする。
T-02（フォールバック階段）の「発見表現」と同じ仕組みで実装できる。

---

### P-07 週次リセットで実際に何が起きるのか

**決めること**: リセットの瞬間のユーザー体験。

未定義な点:
- 先週の順位は消えるのか、称号として残るのか（`ranking_entries` は残す設計なので技術的には可能）
- リセットの通知はするのか（T-27 と接続）
- 「先週1位だった人」に何かあるのか
- 全部門が同時にリセットされるのか、部門ごとにずらすのか

**推奨**: 月曜の朝に「先週の結果」を通知し、称号を配布して、同時に今週の椅子が空いたことを見せる。
**リセットは喪失ではなく、週次の再挑戦機会として提示する。** リテンションの主軸になり得る唯一の
定期イベントなので、ここは丁寧に設計する価値がある。

---

### P-08 モデレーションと安全の運用方針

**決めること**: 誰が、何を、どの基準で止めるのか。個人開発で運用可能な範囲で。

docs/04 で**技術的な仕組み**（trust_score、ブロックリスト、レビューキュー）は設計したが、
**運用ポリシー**が無い。

未定義な点:
- 通報機能を持つか（docs/04 §10 で「プロダクト仕様側で設計」として保留した）
- レビューキューを誰がいつ処理するのか（1人運用。滞留48時間でアラートは設定済み）
- **危険行為の助長への態度**。絶景スポットの共有は、立入禁止区域・私有地・
  危険な崖への誘導になり得る。「スポットを教えるアプリ」の構造的リスク
- 不適切コンテンツ（風景以外の投稿）の扱い

**推奨**: MVPでは**通報機能を必ず入れる**（1人運用だからこそ、検知をユーザーに頼る）。
危険地点は docs/04 の `location_blocklist` で `reject` にできるが、
**事前に全部は登録できない**ので、通報起点で追加する運用が現実的。

## D. 判断の順序（推奨）

```
P-01 ターゲットと地理スコープ
  ├─→ P-02 ホーム画面の構成 ─→ P-03 ソーシャルグラフ
  │      └─→ P-04 投票の供給（T-09 と一体で決める）
  ├─→ P-05 投稿頻度と過去写真（→ 0005 の期間判定を captured_at に変更）
  └─→ P-06 コールドスタート ─→ P-07 週次リセットの体験 ─→ T-25 称号 / T-27 通知
                                   P-08 モデレーション（並行）
```

**P-01 が全ての起点。** これが決まらないと、技術側の数値（H3解像度、足切り件数、
密度の閾値）を実データで検証しようにも、そもそもどこのデータを集めるかが決まらない。

**次に P-04。** ③が成立しないとハイブリッド採点の前提が崩れ、
日本向けファインチューニング（引継ぎ書§6の制約への回答）の原資も得られない。
**技術的にはすでに実装済みなのに、プロダクトとして供給が設計されていない**という
一番危険な状態にある。

## 補足: この文書に無いもの

意図的に扱っていないもの —— UI/UXの具体（画面遷移・ビジュアル）、ブランディング、
アプリ名、ローンチ計画、法務（利用規約・プライバシーポリシーの文面）。
これらは上記が決まった後に着手すべきもので、順序を逆にすると作り直しになる。
