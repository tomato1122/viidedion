## A. 決定の詳細

### P-01 ターゲットユーザーと地理スコープ

**決定: 全国 × ライト層（旅行・ドライブ層）**

密度を作りにくい選択であることを認識した上での判断。以下がその帰結として確定した。

| # | 帰結 |
|---|---|
| 1 | **T-02 のフォールバックが「例外処理」ではなく「主経路」になる。** 順位が出ないのが通常状態 |
| 2 | **体験が二極化する。** 有名スポットは「ランキング成立するが希少性②の base ≒ 0」、無名スポットは「希少性満点だがランキング不成立」 |
| 3 | **原則3（後発でも1位・発見者になれる）は、ランキングではなく「発見」が担う**（→ P-06 でその手段を確定） |
| 4 | 週次リセットの重要度が相対的に下がる（→ P-07 で発見を主役に） |
| 5 | 危険地点・保護地域の**全国手動登録は不可能**（`docs/04 SEC-PRIV-04` の前提が崩れる → P-08 / P-09） |
| 6 | 比較投票のペアは**ファセット内で組めるケースが少数派**になる（→ P-04b） |

**週次ランキング成立に必要な密度（試算）**: `rebuild_ranking_entries` は当該期間の投稿のみを対象に
足切り5件を適用する。1週間では季節が固定されるため、ファセットは実質「方位(最大9) × 天候(最大6) ×
時間帯(6)」。投稿が1〜2ファセットに集中する場合で**週5〜10件/スポット**、5〜10ファセットに
分散する場合で**週25〜50件/スポット**が必要になる。

### P-03 ソーシャルグラフ

**決定: スポットのみフォロー（人はフォローしない）**

原則2（フォロワー数が権力にならない）を、運用ではなく**構造で担保**する。
フォロワー数という概念がスキーマに存在しない状態になる。

| # | 帰結 |
|---|---|
| 1 | `spot_follows` テーブルを追加（未実装。`spot_identity` を指す — T-01 の永続IDと一体で扱う） |
| 2 | 「フォロー中スポットの新記録」が **T-27 通知の原資**になる |
| 3 | スポットフォロー＋訪問履歴が **P-04 の票の重み付け**に使える（引継ぎ書 §2③） |
| 4 | **人づての拡散が起きない** → アプリ外シェア機能が必要（→ T-34） |

**変更容易性**: 人フォローの追加は容易（テーブル追加）。逆に削除は実質不可逆。迷うなら本決定が低リスク。

### P-04 比較投票の供給

**決定: 投稿フローに組み込む（スキップ可）＋ 補助として独立した軽い投票導線を併設**

投稿完了後に「3枚選ぶ」を提示する。スキップ可能にして義務感を避ける。

**採用理由**: 需給が構造的に均衡する唯一の案。投稿が増えれば必要な票も増えるが、
供給元も同時に増える。また投稿フローは地図から独立しているため、P-02=B の制約を受けない。

| # | 帰結 |
|---|---|
| 1 | 投稿API（T-19）に投票ステップを組み込む。スキップ率の計測が必要 |
| 2 | **閲覧専用ユーザーの票が取れない**ため、独立導線を補助として併設する |
| 3 | `votes.weight` の CHECK 制約が `weight = 0`（スキップ相当）を許すか要確認。実装時に検証する |

**必要な供給量の目安**: `community_shrink_m = 8` から逆算すると、1投稿あたり15〜30票、
1回の比較が2票を生むため、**アクティブユーザー1人あたり2〜3回/日**の投票が必要。

これは T-30（初期ユーザーゼロ期の体験設計）の設計案 (c)「投票を投稿の対価にする」が
実質的に採用されたことを意味する。P-04 の決定を正とし、T-30 (c) の実装として扱う。

### P-04b 比較ペアの構成

**決定: 階層的ペア構成 ＋ 橋渡し**

サーバーがペアを選ぶ（`docs/04 SEC-VOTE-01`）ときの引き方を次の優先順位で決める。

| 段 | 引く範囲 | 位置づけ |
|---|---|---|
| 1 | 同一ファセット（スポット × 方位 × 天候 × 時間帯 × 季節） | **主戦場** |
| 2 | 同一スポット（条件は問わない） | **主戦場** |
| 3 | **同じ時間帯 × 天候の別スポット** | フォールバック |
| 4 | 横断（橋渡し。比較グラフの接続性を保つため意図的に混ぜる） | 最終段 |

**第3段を「何でもいいから別スポット」ではなく「同じ時間帯×天候の別スポット」と定義する**のが要点。
「雪の峠 vs 夏の海岸」ではなく「**別々の場所の、同じ朝焼け**」を比べる形にすることで、
場所が違っても比較の意味が保たれ、①AI採点との役割の重複を避けられる。

詳細と Elo の解釈の変化は [ADR-0004](adr/0004-comparison-pair-composition.md)。

**確定した帰結**:

| # | 帰結 |
|---|---|
| 1 | `votes` に `pair_tier` とファセット列を追加する設計（現在のコメントは「どのファセットの比較か」と書いてあるが実装が伴っていない）。**実装は T-09 選定後** |
| 2 | **自己投票の除外が必要**（`docs/04 SEC-VOTE-01` に追記済み）。現状コードに一切の防御がない |
| 3 | **相互投票ループの検知が必要**（`docs/04 SEC-VOTE-03` に追記済み） |
| 4 | T-02（ランキングの階段）とは**段数が違う**。T-02 の最終段は「順位を出さない」だが、本決定の最終段は「常に成立する」。実装で共通化しすぎない |
| 5 | `post_community_scores.elo_rating` は1列のままでよい（投稿は1ファセットに属するため）。**スキーマ変更不要** |

**認識済みのトレードオフ**: 第1〜2段を主戦場に据えたため、投稿が少ないスポットでは③に票が
ほとんど入らない。縮約により③は10点前後に張り付き、**多くの投稿で実質「①+②」が点数を決める**。
これは破綻ではなく「①②が主・③が補正」という構成になるだけだが、意図した姿である。

### P-05 過去に撮影した写真の扱い

**決定: 猶予つき撮影日ベース。猶予 N = 30日**

- ランキング期間の判定を `posted_at` → **`captured_at`** に変更する
- 撮影から**30日以内**の投稿をランキング対象とする
- `docs/04` の `exif_time_match` **7日ルールは撤廃**し、30日と整合させる
- 猶予を超えた投稿は**ランキング対象外だが、投稿も②希少性も有効**
- **EXIF が無い写真**は撮影日時不明のため期間に割り当てられない。投稿は許可するが
  ランキング対象外・「初」ボーナス対象外（既存の `p_eligible = false` に一致）

詳細は [ADR-0001](adr/0001-ranking-period-by-captured-at.md)。

**採用理由**: `captured_at` は既に `posts` に NOT NULL で存在し、季節・天候・時間帯の
ファセット導出も全て `captured_at` 基準。**ランキングだけが `posted_at` を見ているのが不整合**だった。
旅行後のまとめ投稿は P-01=C の主要ユーザーの標準行動であり、7日ルールはそれを減点していた。

**必要な追加実装**: 週締め後に過去写真が入ってくるため、`ranking_periods.closed_at` を使った
**確定スナップショット**が必要（→ T-35）。**未実装。** ADR-0001 の対応（`rebuild_ranking_entries`
の期間判定変更・`trust_rulesets` の閾値変更）自体も未実装（下記「実装状況」参照）。

**実装状況（2026-08-14 時点）**: 決定は確定しているが、コードへの反映は未了。
`db/migrations/0009_ranking_fallback.sql` の `rebuild_ranking_entries` は依然 `posted_at`
基準のまま。`0011_trust_and_privacy.sql` の `trust_rulesets` は依然 `th_exif_time_days = 7`
のまま。既存のスモークテスト・`core/` の統合テストは `posted_at` 基準を前提に組んであるため、
変更時はテストの立て直しが伴う。実装タスクとして次回以降に持ち越す。

### P-06 コールドスタート

**決定: POI由来の未踏スポットを先に地図へ置く**

投稿ゼロでも展望台・峠・湖・岬などを地図にピン表示し、「まだ誰も記録していない」と示す。

**採用理由**: P-02=B を選んだ以上、地図が空であることは許容できない。また未踏スポットは
②希少性の base が満点になる場所であり、**原則3（発見者になれる）をランキングではなく
発見で担保する**唯一の現実的な手段。P-01 の帰結2・3への回答でもある。

| # | 帰結 |
|---|---|
| 1 | ~~T-05 が最優先タスクに確定~~ → **2026-08-13 完了。[ADR-001](../06-adr-poi-source.md) で OpenStreetMap を採用**（実装: `db/migrations/0010_poi_source_terms.sql`） |
| 2 | ~~T-05 の結論次第で本決定の再判断が必要~~ → **再判断は不要。本決定はそのまま維持できる** |
| 3 | `spots` に**投稿ゼロのレコードを作る**設計判断が発生（T-01 の永続ID設計と一体で扱う。`spot_identity` は投稿数と独立して存在できるため、この決定は既存実装のままで満たされている） |
| 4 | OSM 由来データは自前テーブルに分離し、ODbL の share-alike がアプリ独自データへ波及しないようにする（実装: `poi_reference` / `poi_extract_versions`。`spots` 側は `source_code` で出自を判別する） |
| 5 | **クライアントに帰属表示が必須**（「OpenStreetMap」を `openstreetmap.org/copyright` へリンクし地図の隅に常時表示。DB側は `v_poi_license_compliance` で欠落を検知する） |

**実データ密度の裏付け**（Overpass API で実測、2026-08-13）: 日本国内の
`tourism=viewpoint` 6,658件 / `natural=cape` 1,617件。空白の地図を埋めるには十分。

**地図タイル配信は別問題。** OSM のデータを使うことと OSM のタイルサーバーを使うことは別。
`tile.openstreetmap.org` は bulk download 禁止・SLA なしで本番利用不可（→ T-33）。

### P-07 週次リセットのユーザー体験

**決定: 週次を維持し、「発見」を主役にする**

- **残す**: 過去の順位（`ranking_entries` は削除しない）、称号、自己ベスト
- **リセットする**: 今週の部門順位のみ
- **月曜朝の通知**: ①今週あなたが最初に記録した場所、②フォロー中スポットの新記録、
  ③（成立していれば）先週の部門結果

**採用理由**: 実装済みの週次機構（`open_next_ranking_period` / `rebuild_ranking_entries`）を
そのまま使えるため変更コストがゼロ。また P-06 で発見を原則3の担い手にすると決めた以上、
週次通知の主役も発見にするのが筋。ランキングは「成立したら嬉しいボーナス」の位置づけに下げる。

**変更容易性**: `ranking_period_kind` に `monthly` が既に存在し、`ranking_entries` も
期間IDで分離済みのため、**後から月次を追加するのは容易**。実データを見てから判断できる。

### P-08 モデレーション

**決定: MVP では通報機能を実装しない。ただし公開ローンチ前の必須ゲートとして記録する**

未公開のプロトタイプ段階では通報機能に工数を割かない、というスコープ判断。

**ただし次を明記する**:

- **通報機能（→ T-34）は「MVP対象外」ではなく「公開ローンチ前に必須」**。危険地点・私有地への
  誘導リスクは公開した瞬間に発生し、その時点では既に公開済みコンテンツへの対処に追われる
- `docs/04 SEC-PRIV-04` の `location_blocklist`（`reject` 指定で投稿自体を拒否）は設計・実装済み
  （`0011_trust_and_privacy.sql`）のため、**運営が把握している危険地点だけは通報なしでも塞げる**。
  全国を網羅はできないがゼロではない
- MVP 期間中は trust_score の自動判定（`docs/04 §6`。実装: `0011` の `calc_trust_score`）
  のみが防御線になる

### P-09 物理的な安全と誘導リスク

**「初期のポケモンGOのようにならないか」という問いから派生した論点。**

**構造**: 「未踏スポットの地図表示（P-06）」×「②の初回ボーナス」= **現地へ急がせるインセンティブ**。
地図に「まだ誰も記録していない」と示し、そこに先着報酬を置くと、対象が峠・崖・岬である以上、
深夜や悪天候での移動を促しかねない。P-08=C（通報なし）と重なる。

**ただし現行設計は既にかなり緩和している**:

| 緩和要因 | 内容 |
|---|---|
| 「初」はファセット単位 | スポット単位の早い者勝ちではない。同じ峠でも方位・天候・時間帯が違えば別の「初」が取れる |
| 希少性の減衰が緩やか | `base` は対数逓減。1人目18点、2人目でも約16点。独占構造ではない |
| `timeslot` に `night` がある | 夜間の「初」だけ扱いを変えることが技術的に可能 |
| `location_blocklist` | `reject` 指定で投稿自体を拒否できる（設計・実装済み） |

**参考: 初期ポケモンGOとの差**: あちらの「地方に何もない」問題はスポットが Ingress の
クラウドソースデータ由来で、既存プレイヤーが都市に偏っていたことに起因する。
本アプリは POI（展望台・峠・湖・岬・滝）由来であり、**景勝地はむしろ地方に多い**ため、
スポット分布の偏りは逆方向に働く。ただし**人の分布は都市偏重**なので、
「スポットは地方に多いが投稿する人は都市にいる」というミスマッチは残る。

**決める必要があること**:
- 危険カテゴリ（崖・岩場・立入制限区域）の事前ブロックをどこまでやるか
- 夜間の「初」ボーナスを抑制するか
- 未踏スポット表示に安全情報を添えるか

**期限**: 公開ローンチ前。MVP の実装は本決定を待たずに進められる。
